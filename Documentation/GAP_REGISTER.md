## Headline for the CEO

The platform has **real, well-engineered depth in the middle** (payment orchestration, scheme adapters, settlement generation + reconciliation, commission-share config, the 8-step admin onboarding wizard, bitemporal config schema, ADR-016 anti-double-charge discipline) and is **hollow at both ends**: there is effectively **no authentication** in front of it, and **no production environment, monitoring, or backup** under it. Revenue booking on the newest corridor is miscategorised and lossy, and the partner-facing portal is largely fixtures.

**It is demoable. It is not sellable-with-a-signature yet.** The credible near-term sale is *operator-led onboarding + ZeroPay KRW pay-in*, demoed from the admin wizard, with everything else on a dated roadmap.

Blocker counts by lens: CPO 9 · CFO 3 · COO 5 · CISO 9 (overlaps consolidated below).

  <br>***Architectural limit, stated rather than papered over.** HMAC-SHA256 requires the verifier to hold the *plaintext* secret, and the real store deliberately cannot supply one: `api_keys` stores only a salted PBKDF2-HMAC-SHA256 digest and auth-identity discards the plaintext at issuance (SEC-09 §4 — the property the CISO audit named as genuinely solid and worth protecting). So auth-identity is authoritative for **identity + lifecycle**, while HMAC signing material and the per-partner edge policy the store does not model (IP CIDR ranges, mTLS fingerprint, quote TTL) come from operator-supplied `gateway.partner-credentials.partners[]` with `hmac-secret` injected from the environment. **A key is accepted only if it appears in BOTH**, which is strictly stronger than the one hard-coded map it replaces. Consequence, stated plainly: the partner API authenticates **nobody** until an operator populates that table — the correct fail-closed posture, and the reason this is `[~]` and not `[x]`. Making one component both the authoritative store and the HMAC verifier needs a reversibly-encrypted secret column (schema migration + a KMS-held key), which is T1-6 territory, not a config change.*

  <br>***The security posture was decided explicitly, not defaulted into.** Making Redis the store makes "Redis is down" a question the edge must answer, and the two obvious answers are both bad: "no rate limiting" silently undoes T0-7 and "the platform 503s" invents a single point of failure. So each control names its own posture and **both defaults are the T0-7-consistent ones**. Rate limit: `gateway.rate-limit.on-store-error` = **`deny`** (default; 429, unchanged from `fail-open: false`, which still means `allow` so a deployment that set it keeps what it configured) | `local` (degrade to the per-JVM window — cap becomes N× but is still a cap; **this is the recommended setting for a multi-replica deployment that judges a Redis outage worse than an N× cap**, and it is the option a boolean could not express) | `allow`.
