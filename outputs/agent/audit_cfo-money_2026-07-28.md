# GMEPay+ CFO Money Audit — 2026-07-28

Lens: is the money right, auditable, and is revenue actually collectable? All findings verified against code (paths below), not docs.

Scope read: `services/revenue-ledger`, `services/settlement-reconciliation`, `services/prefunding`, `services/payment-executor` (PaymentOrchestrator, SendmnPaymentService), `services/scheme-adapter-{zeropay,sendmn,ninepay}`, `services/config-registry` (commercial/fee), `services/rate-fx`, `Documentation/SETTLEMENT_FLOW_SPEC.md`, `Documentation/schemes/QR_SCHEME_ACCOMMODATION_PLAN.md`.

What is genuinely solid (credit where due): revenue-ledger journals are balance-validated per currency (`Journal.assertBalanced`); rounding-residual posting is idempotent with a DB partial-unique backstop (Flyway V006); prefunding uses row-locked, idempotent reserve/capture/release/deduct/reverse with a full entry ledger; the ZeroPay MPM path is a real two-phase authorize→confirm with the scheme submit last, service fee folded into the float hold, and ZP0061/0063/0065/0066 generation is tie-out-disciplined (detail files sourced from request-batch lines). The gaps below sit around that core.

---

## Ranked gaps

### 1. [BLOCKER-for-revenue] SENDMN revenue is booked as "rounding residual" — miscategorized and invisible as revenue
**Evidence:** `D:\GMEPay+\code\services\payment-executor\src\main\java\com\gme\pay\payment\domain\SendmnPaymentService.java` lines 310–326 — FX margin AND the ₩500 service fee are both posted via `revenueLedgerClient.postRoundingResidual(txnRef, fxMarginKrw, "KRW")` / `postRoundingResidual(txnRef + "-FEE", FEE_KRW, "KRW")`. In `revenue-ledger` that lands in account `REVENUE_ROUNDING` (`LedgerPostingService.java:34,62-89`), an account whose documented meaning is "rounding gain/loss vs partner booking". The proper accounts `REVENUE_FX_MARGIN` / `REVENUE_SERVICE_CHARGE` exist but are never hit for SENDMN. Meanwhile the SENDMN `commitStatus` carries **null margins** (SendmnPaymentService.java:290-303, the 5-arg StatusPatch), so the `payment.approved` → revenue-record path captures **zero** SENDMN revenue. Consequence: SENDMN P&L is (a) categorically wrong in the journals (margin+fee indistinguishable from rounding noise), (b) zero in the revenue-records/summary surface, and (c) posted fire-and-forget with no retry (see gap 6) — a failed POST silently loses the revenue record entirely.
**Done =** SENDMN commit posts a proper revenue capture (fxMargin→`REVENUE_FX_MARGIN`-equivalent record + fee→service-charge) with real margins on the StatusPatch so the payment.approved event carries them; `REVENUE_ROUNDING` receives only true residuals; a backfill/reclass journal for anything already booked.

### 2. [BLOCKER-for-revenue] No settlement or reconciliation feed at all for SendMN (USD) and 9Pay (VND) — money owed cross-border is untied
**Evidence:** `grep sendmn|ninepay` over `services/settlement-reconciliation/src/main` returns **zero** hits — the entire settlement service (builders, parsers, ReconDiffEngine, schedulers) is ZeroPay-only (ZP006x). `Documentation/schemes/QR_SCHEME_ACCOMMODATION_PLAN.md:62` — "Settlement: SendMN settles USD vs registered rate — needs recon feed (doc silent on file format → OPEN with SendMN)"; O4 (recon file format) unresolved. Worse, there is a **rate-basis mismatch nobody reconciles**: the USD GME owes SendMN is computed adapter-side at the SendMN-**registered** buy rate (`scheme-adapter-sendmn/.../SendmnSchemeAdapter.java:163-177`, `settlementAmount = fxRates.settlementAmount(localAmount, rate.getRate())`), while the USD deducted from the partner float uses a **live USD/KRW rate with a hardcoded 1350 fallback** (`SendmnPaymentService.java:64-65,190-193,353-365`). The spread between those two USD figures is booked nowhere and no daily process would surface it. 9Pay has no recon of any kind.
**Done =** per-scheme settlement obligation ledger (USD owed SendMN at registered rate, VND paid via 9Pay) + a daily tie-out job: adapter settlement amounts vs prefund captures vs scheme statement (once O4 format arrives); mismatch → recon exception queue.

### 3. [BLOCKER-for-revenue] 9Pay IPN 009 (post-SUCCESS bank reversal) never reaches the hub — bank-returned money is not restored to the float or the ledger
**Evidence:** `scheme-adapter-ninepay/.../adapter/NinepaySchemeAdapter.java:203-247` — on code 009 the adapter maps to `REVERSED`, stamps `reversed_at` on the payout row, saves the IPN event, and returns an ACK. Nothing else happens: `grep ninepay` over `payment-executor/src/main` and `prefunding/src/main` returns zero hits — there is no hub-side event, no `prefundingClient.reverse`/`releaseReversedFloat`, no transaction-mgmt status flip, no `postReversalJournal`. The plumbing exists on the hub (prefunding's `releaseReversedFloat` + the `payment.reversed` Kafka consumer, `PrefundingService.java:203-225`) but nothing 9Pay-shaped feeds it. A bank reversal means GME got the VND back while the books still show the payout consumed the float and revenue stands — customer/partner money is silently stranded on GME's side (or vice versa depending on flow direction).
**Done =** 009 IPN raises a hub event (adapter → outbox → `payment.reversed` or a scheme-callback seam) that flips the transaction, restores/adjusts prefunding, and posts the reversal journal; E2E covering 009-after-SUCCESS.

### 4. [MAJOR] Commission split: wired but silently skippable, record-only (no journal), and fed a config rate instead of the scheme's actual fee
**Evidence:** Live wiring exists — `PaymentOrchestrator.postCommissionSplit` (PaymentOrchestrator.java:384-399) runs at confirm — but it **silently no-ops** when: payout isn't KRW, no merchant-fee rate was snapshotted, or config-registry doesn't resolve both shares. Nothing counts or reports skipped splits. The endpoint writes only a `commission_splits` record — "it does NOT post the double-entry journal (that remains LedgerPostingService.postFeeShareSplit)" (`CommissionSplitController.java:26`), and `postFeeShareSplit` has **zero production callers** (grep). Spec D11 says for ZeroPay the scheme **returns** the merchant fee (전문 field 41) and GME must not compute it — the adapter does receive `merchantFeeKrw` off the wire (`ZeroPaySchemeAdapter.java:380,700`) but the hub contract `SchemeClient.MpmSubmitResponse` has **no merchant-fee field**, so the split is computed from the config-resolved rate, which can drift from what ZeroPay actually charged. Merchant-fee sync (ZP0045) is unbuilt (`Documentation/services_backlog/platform-infra.md:3248`). Leakage: GME's 70% cut is calculated on a possibly-wrong base and never journaled as receivable/payable.
**Done =** merchantFeeKrw carried on MpmSubmitResponse → split computed off the scheme figure; skipped-split counter/report; splits post the fee-share journal (or an explicit decision that records suffice, documented).

### 5. [MAJOR] Merchant MDR billing/receivables subsystem does not exist — one of the three revenue streams has no collection mechanism
**Evidence:** SETTLEMENT_FLOW_SPEC §2 D9/D11 and §7.5: MDR is billed to the merchant out-of-band (accrue → invoice → collect), then a cut shared with ZeroPay. Grep for merchant-billing/invoice/receivable across services: the only invoice code is Hometax **tax**-invoice reporting (`reporting-compliance/.../hometax/`). No accrual table, no invoice run, no receivables aging, no collections status. MDR revenue is currently recognizable (via commission-split records) but not **collectable** — there is no path from "GME is owed ₩X by merchant Y" to cash.
**Done =** merchant receivables ledger (accrue per txn from the split), periodic invoice generation, payment matching, aging report; ZeroPay-share payable accrued alongside.

### 6. [MAJOR] All hot-path ledger postings are fire-and-forget with no replay job — "retriable offline" is a comment, not a mechanism
**Evidence:** `RestRevenueLedgerClient.java` swallows every failure on all four surfaces (rounding residual :65-73, revenue capture :100-106, commission split :131-137, reversal journal :156-163) with comments like "retriable offline" / "replayed by an out-of-band job". No such job exists: no scheduler, no outbox, no dead-letter in payment-executor (its event publisher is still `LogEventPublisher`, `EventPublisherConfig.java:16`). The only durable path is revenue-capture via transaction-mgmt's outbox → `payment.approved` → the idempotent Kafka consumer (good). Rounding residuals, commission splits and reversal journals have **only** the lossy REST call — a revenue-ledger outage during peak drops those postings permanently, detectable only by log-mining.
**Done =** either route residual/split/reversal through the transaction-mgmt outbox events, or build the replay sweeper that re-posts from the residual/booking fields persisted on transactions; a daily "posted vs approved-txn" completeness check.

### 7. [MAJOR] The double-entry ledger does not carry the main P&L — production revenue lives in a single-entry record store
**Evidence:** `RevenueCaptureService.java:25-27` — "**Not double-entry.** This writes the per-transaction revenue audit row only; it does NOT post balanced journals via LedgerPostingService (mixing the two would double-count)." `LedgerPostingService.postRevenueCapture` and `postFeeShareSplit` (the balanced FX-margin/service-charge/fee-share journals) have **no production callers** — grep hits are only the client-side method (which posts to `/v1/revenue/capture`, i.e. the record store), docs and tests. In production, journals receive **only** rounding residuals and cancel/refund reversals. Consequence: no trial balance is possible; `RECEIVABLE_PARTNER` is credited by reversals/residuals that were never debited by a matching revenue journal, so the journal ledger, read alone, is internally inconsistent as a book of account.
**Done =** decide the system of record: either (a) revenue capture also posts the balanced journal (and the record becomes a view), or (b) the record store is formally the revenue subledger and journals are scoped/renamed to residual+reversal only — and a period-end trial-balance/day-close report exists over whichever is chosen.

### 8. [MAJOR] SETTLEMENT_FLOW_SPEC vs code: the two-phase spine is built for MPM, but CPM, float currency, and refund edges are not
**Evidence:** Spec (2026-06-24) §7 deltas vs code today: ✅ built — two-phase authorize/confirm with scheme-submit-last (`PaymentOrchestrator.authorizeMpm/confirmMpm`), reserve/capture/release ledger (`PrefundingService` §7.1), scheme balance-check gate, service fee folded into the hold (§7.4 fix, PaymentOrchestrator.java:243-249), authorization expiry sweeper, ZeroPay 전문/TCP codec (`jeonmun/JeonmunCodec.java`, `transport/ZeroPayTcpTransport.java`). ❌ not built — CPM is still single-shot `executeCpm` (PaymentOrchestrator.java:487+, reserve added but no partner-confirm phase, and the header comment admits "CPM still uses the single-shot … until its two-phase rebuild"); float currency is hardcoded USD (`PrefundingService.pushPartnerLimits` creates rows with `"USD"`, :465) so a KRW-settling partner (D3) is unsupported; scheme-outage-after-charge auto-refund (§4.1 "the only ugly case") not implemented; refund window/partial refunds still open (§8).
**Done =** CPM two-phase parity, configurable float currency = `settle_a_ccy`, the auto-refund compensation path, and a refund policy decision.

### 9. [MAJOR] Zero FX exposure tracking — GME bears FX risk (D4) on MNT/VND/KRW with no measurement, and a hardcoded fallback rate
**Evidence:** Grep for exposure/hedge/unhedged across all services: no hits (one false positive in an HMAC filter). No open-position table, no daily FX P&L, nothing distinguishing Phase-1 locked margin from Phase-2 trading gain on these corridors. Compounding: `SendmnPaymentService.KRW_PER_USD = 1350` (line 65) silently prices the USD float deduction when the rate provider is down — during a KRW move, every SENDMN payment mis-prices the deduction with no flag on the transaction that a fallback was used.
**Done =** per-currency open-position report (float balances, in-flight settlement obligations, registered vs live rate deltas); fallback-rate usage flagged on the txn + alerted; treasury sign-off on the fallback constant.

### 10. [MAJOR] No three-way daily finance reconciliation (scheme ↔ ledger ↔ prefunding) or day-close report
**Evidence:** What exists: `ReconDiffEngine` matches ZeroPay result files vs hub transactions (one leg, one scheme); `JournalViewController`/`RevenueController` give browse/summary; recon breaks alert (`ReconBreakAlerter`). What doesn't: nothing compares prefunding ledger movement vs revenue-ledger postings vs transaction-mgmt for a business day; no trial balance; no day-close artifact finance can sign. A one-sided failure (e.g. capture succeeded, revenue post dropped — gap 6) is invisible to any current report.
**Done =** a daily close job emitting: per-partner float movement vs captured txn sum, journal debits=credits by account, revenue records vs approved txns, recon exceptions outstanding — persisted and exportable.

### 11. [MINOR] SENDMN fee/margin hardcoded (₩500 + 2% default) — config-registry fee schedules don't govern the live wallet path
**Evidence:** `SendmnPaymentService.java:62` `FEE_KRW = 500` (compile-time constant) and `:99` `@Value("${gmepay.payment.sendmn.fx-margin:0.02}")`. Config-registry has the real machinery — `partner_fee_schedule` V018 (`FeeScheduleService`, fixed+bps+tiers) and per-scheme `serviceChargeUsd` consumed by rate-fx quotes (`QuoteIssueService.java:93-99`) — but the SENDMN path reads none of it. A fee change negotiated with SendMN requires a redeploy, and the admin UI's configured numbers do not describe what customers are actually charged.
**Done =** SENDMN pay resolves fee+margin from config-registry (with the current values seeded), constants demoted to last-resort fallbacks that alert when used.

### 12. [MINOR] SENDMN prefund-reverse failure on scheme decline is log-only — combined with gap 2, the money is unrecoverable by process
**Evidence:** `SendmnPaymentService.java:229-234` and :257-262 — `prefundingClient.reverse` failure is caught and `log.error`'d, payment returns DECLINED, and no compensation record is queued. On the ZeroPay path recon would eventually catch a stuck hold; SENDMN has no recon (gap 2), so a failed reverse permanently overstates GME's claim on the partner float until someone greps logs.
**Done =** failed reversals persist a compensation row (or ride the outbox) retried until confirmed; count surfaced on the ops dashboard.

### 13. [MINOR] CPM path skips the per-transaction and AML cumulative limit gates
**Evidence:** `PaymentOrchestrator.executeCpm` NOTE (lines 489-491): the limit gate is not applied because CpmPaymentCommand lacks partnerCode. The MPM path enforces the statutory 소액해외송금업 per-txn cap and daily/monthly/annual cumulative caps (`:220-275`); CPM enforces neither — a regulatory-cap bypass with monetary consequence if CPM goes live cross-border.
**Done =** partnerCode threaded into the CPM command; both gates applied before the reserve.

### 14. [MINOR] `LedgerPostingService.postRevenueCapture`/`postFeeShareSplit` are not idempotent and write zero-amount noise journals
**Evidence:** Unlike `postRoundingResidual` (reference-guarded + V006 unique index), `postRevenueCapture` (LedgerPostingService.java:134-165) and `postFeeShareSplit` (:190-220) have no duplicate guard, and both write a "nominal balanced journal" of 0.0000 on zero revenue (:157-161, :204-209). Latent today (no production callers — gap 7) but the moment gap 7's option (a) wires them, replays double-book.
**Done =** reference-scoped idempotency (matching V006 pattern) on both; drop or flag zero-amount journals.

### 15. [MINOR] SENDMN MNT rounding residual is silently absorbed — inconsistent with the platform's own residual discipline
**Evidence:** `SendmnPaymentService.java:179-185` — MNT payout is rounded HALF_UP to whole MNT and `fxMarginKrw = amountKrw × margin` is booked independently; the difference between the theoretical and rounded MNT payout (the true rounding residual, in MNT) is never computed or posted, unlike the ZeroPay path where every booking residual is captured via `SettlementBookingService` + `postRoundingResidual` (PaymentOrchestrator.java:331-353). Small per-txn, but it is exactly the class of leak the REVENUE_ROUNDING account was built to make visible.
**Done =** SENDMN books the MNT rounding residual through the same residual API (correctly keyed), keeping REVENUE_ROUNDING complete across schemes.
